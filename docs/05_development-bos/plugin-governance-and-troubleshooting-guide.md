插件是金蝶 BOS/苍穹二开里最灵活、也最容易失控的一层。一个保存插件可能影响单据状态，一个审核后插件可能影响库存、接口、凭证和月结，一个字段写回可能让报表、下推和对账都出现隐性差异。

这篇不是替代“插件开发入门”，而是用于项目交付和生产维护：需求评审时判断该不该写插件，开发时控制幂等、事务、日志和权限，上线后能快速定位“插件不执行、字段没带出、重复推送、审核卡住、性能变慢”等问题。

## 二、插件治理的核心原则

先把插件当成“系统行为变更”管理，而不是当成“一段代码”管理。

```text
业务需求
  -> 标准功能是否可做
  -> 参数/规则/工作流/单据转换是否可做
  -> 插件是否真的必要
  -> 插件影响哪些单据、接口、凭证、报表、权限
  -> 开发、测试、发布、监控、回滚
```

### 什么时候不要急着写插件

| 需求 | 优先尝试 |
| --- | --- |
| 字段必填、简单格式校验 | 字段属性、表单规则、校验规则 |
| 字段显示隐藏、只读控制 | 表单配置、权限、页面规则 |
| 固定审批路线 | 工作流配置 |
| 上下游字段带入 | 单据转换字段映射 |
| 报表新增展示字段 | 报表数据源、查询方案 |
| 外部系统导入基础数据 | 标准导入、WebAPI、集成平台 |
| 临时批量修数据 | 经审批的数据修复方案，不优先写业务插件 |

### 什么时候适合写插件

| 场景 | 插件价值 | 关键控制 |
| --- | --- | --- |
| 跨分录、跨单据校验 | 标准校验难覆盖 | 性能、提示、事务 |
| 审核后生成辅助数据 | 需要强业务规则 | 幂等、日志、反审核 |
| 下推前补特殊字段 | 标准映射不足 | 源单关联、字段存在性 |
| 调外部接口 | 需要同步或通知外部系统 | 超时、重试、对账、幂等 |
| 批量后台处理 | 前台操作不能承受 | 分批、状态、补偿 |
| 特殊权限控制 | 标准权限无法表达 | 可解释、可审计 |

## 三、插件类型选择表

官方 SDK 层级能看到多类动态表单插件入口。项目里可以按“触发对象”选择：

| 插件类型 | 常见基类或入口 | 适合做 | 不适合做 |
| --- | --- | --- | --- |
| 表单插件 | `AbstractBillPlugIn`、动态表单插件 | 页面初始化、字段联动、按钮控制、前台提示 | 大量查库、复杂事务、后台批处理 |
| 列表插件 | `AbstractListPlugIn` | 列表按钮、批量操作入口、过滤条件扩展 | 每行都查大量业务数据 |
| 操作服务插件 | `AbstractOperationServicePlugIn` | 保存、提交、审核、反审核前后校验和处理 | 长时间外部接口阻塞、无幂等创建 |
| 单据转换插件 | 转换规则相关插件 | 下推、字段特殊映射、源单关系处理 | 绕过标准转换直接造下游单 |
| 服务插件/后台任务 | 服务层、调度任务 | 批处理、补偿、定时同步 | 依赖前台页面状态 |
| 报表插件 | `AbstractSysReportPlugIn` 等报表插件入口 | 报表参数、数据过滤、展示增强 | 修改核心业务数据 |

简单判断：

```text
用户点按钮前后要处理 -> 表单插件或列表插件
保存/提交/审核动作要处理 -> 操作服务插件
上下游下推要处理 -> 单据转换配置或转换插件
离线批量补偿 -> 后台任务或服务插件
只是展示和查询 -> 报表或列表扩展
```

## 四、事件时机选择

插件治理最容易犯的错，是把逻辑放错时机。放早了数据不完整，放晚了事务不可控，放在前台会卡用户，放在审核后又可能重复执行。

| 时机 | 适合处理 | 风险 |
| --- | --- | --- |
| 页面加载 | 默认值、控件状态、提示 | 不要查大表，不要依赖未加载分录 |
| 字段变更 | 联动计算、带出辅助信息 | 不要调用慢接口，不要写正式业务数据 |
| 保存前 | 必填、格式、基础业务校验 | 不要生成不可回滚的外部数据 |
| 保存后 | 补辅助字段、写轻量日志 | 注意事务是否已提交 |
| 提交前 | 提交条件、附件、审批前置检查 | 不要改核心金额和数量 |
| 审核前 | 关键业务规则、库存/期间/状态检查 | 提示必须让业务用户看懂 |
| 审核后 | 生成下游、推接口、写业务日志 | 必须做幂等和补偿 |
| 反审核前 | 检查下游引用、接口状态、月结期间 | 不要强删下游结果 |
| 删除前 | 检查引用和业务状态 | 必须保留原因 |

### 保存插件和审核插件的区别

| 对比项 | 保存插件 | 审核插件 |
| --- | --- | --- |
| 数据状态 | 可能只是草稿或待提交 | 通常代表业务正式生效 |
| 用户预期 | 保存成功即可继续编辑 | 审核成功后影响下游流程 |
| 适合动作 | 字段补齐、轻量校验、日志 | 生成下游、推送接口、锁定业务规则 |
| 最大风险 | 保存慢、字段错误 | 重复生成、对账差异、反审核困难 |

```text
涉及字段：

影响组织：
影响状态：

```

### 影响范围评审

| 影响面 | 必问问题 |
| --- | --- |
| 单据 | 新增字段是否出现在表头、分录、列表、打印、查询、移动端 |
| 下推 | 源单和源分录关系是否保留，反写是否正确 |
| 财务 | 凭证模板、应收应付、存货核算、月结是否受影响 |
| 接口 | 外部系统是否需要新增字段，接口账号是否有权限 |
| 报表 | 报表数据源、取数口径和过滤条件是否要更新 |
| 权限 | 菜单、按钮、字段、数据权限是否要回归 |
| 运维 | 日志、监控、失败补偿、回滚脚本是否准备 |

## 六、关键技术模式

### 1. 字段读取和写回

字段读写要先确认三个东西：

1. 字段标识是否是当前环境真实标识。
2. 字段在表头还是分录。
3. 当前事件时机下字段是否已经加载。

常见错误：

| 错误 | 后果 |
| --- | --- |
| 表头字段当分录字段读 | 取不到值或取错行 |
| 分录循环里每行查一次库 | 保存或审核明显变慢 |
| 只按名称查基础资料 | 同名数据导致误匹配 |
| 直接覆盖用户手工维护值 | 业务投诉“系统把我填的改了” |

建议：

- 优先用内码、编码、源单关联字段，不用名称做唯一判断。
- 批量收集分录关键值，再一次性查询。
- 写回前判断目标字段是否为空、是否允许覆盖。
- 涉及用户手工值时，保留“系统带出值”和“用户调整值”的边界。

### 2. 源单和源分录关联

跨单据取数的关键不是“查到了数据”，而是“查到的就是当前行对应的源数据”。

```text
当前单据分录
  -> 源单内码 / 源分录内码
  -> 上游单据分录
  -> 上游字段
  -> 写回当前分录
```

没有源分录关联时，容易出现：

- 多行物料相同但工艺不同，带错字段。
- 同一 BOM 多个版本，取到旧版本。
- 合并下推后不知道哪个源行对应哪个目标行。
- 反审核或重新下推后重复写入。

### 3. 幂等控制

审核后、推接口、生成下游、写辅助表都必须考虑幂等。

推荐幂等键：

```text
系统来源 + 单据内码 + 分录内码 + 操作类型 + 目标系统 + 业务组织
```

处理策略：

1. 首次执行：写入处理记录，执行业务逻辑。
2. 重复执行且内容一致：直接返回已成功结果。
3. 重复执行但内容不同：阻断并进入人工处理。
4. 执行超时：先查处理记录和目标系统，再决定重试。

不要只用“单据编号”做幂等。单据编号可能跨组织、跨账套、跨环境重复。

### 4. 事务边界

操作服务插件通常跟保存、提交、审核事务有关，但外部接口、文件写入、消息推送不一定能跟数据库事务一起回滚。

| 动作 | 建议 |
| --- | --- |
| 校验 | 放在事务前，失败就阻断 |
| 写当前单据字段 | 尽量在同一事务内完成 |
| 写业务日志 | 关键日志尽量随事务保存，外部日志可异步补充 |
| 调外部接口 | 能异步就异步；同步调用必须有超时和幂等 |
| 生成下游单据 | 使用标准服务和源单关系，不直接拼数据绕过规则 |
| 补偿任务 | 独立记录状态，可重跑、可停止、可人工接管 |

### 5. 日志字段

关键插件至少记录：

| 字段 | 说明 |
| --- | --- |
| plugin_name | 插件名或类名 |
| bill_formid | 单据标识 |
| bill_id | 单据内码 |
| bill_no | 单据编号 |
| entry_id | 分录内码，分录逻辑必填 |
| operation | 保存、提交、审核、反审核等 |
| org_id | 业务组织 |
| user_id | 操作用户 |
| request_key | 幂等键或请求号 |
| input_summary | 输入摘要，不记录敏感明文 |
| result | 成功、失败、跳过、重试中 |
| error_message | 给技术排查看的错误 |
| user_message | 给用户看的提示 |
| elapsed_ms | 耗时 |

### 6. 异常提示

用户提示要说明“为什么失败、应该找谁、下一步做什么”。

不好：

```text
NullPointerException
```

更好：

```text
第 3 行物料未维护默认仓库，无法提交生产领料单。请先在物料库存信息中维护仓库，或联系供应链管理员确认领料规则。
```

技术日志可以保留堆栈，但前台提示不要只抛技术异常。

## 七、插件排障流程

遇到插件问题，先按下面顺序查，不要直接改代码。

```text
确认现象
  -> 确认环境和版本
  -> 确认插件是否注册
  -> 确认触发操作和时机
  -> 确认测试数据和权限
  -> 查业务日志和系统日志
  -> 复现最小场景
  -> 判断是配置、数据、权限、代码、接口还是环境
```

### 现场信息收集

| 信息 | 示例 |
| --- | --- |
| 环境 | DEV / TEST / UAT / PROD |
| 单据 | 表单标识、单据编号、内码 |
| 操作 | 保存、提交、审核、下推、反审核 |
| 用户 | 用户、角色、组织 |
| 时间 | 精确到分钟，便于查日志 |
| 报错 | 前台原文、后台堆栈 |
| 影响范围 | 单用户、单组织、所有单据、某版本后出现 |
| 复现数据 | 能否复制一张单据复现 |

### 高频现象定位表

| 现象 | 优先判断 | 处理方向 |
| --- | --- | --- |
| 插件完全不执行 | 注册对象、操作绑定、发布包、缓存 | 查元数据绑定和当前环境版本 |
| 保存时字段没带出 | 字段标识、分录行、事件时机、查询条件 | 用最小数据复现并打印关键字段 |
| 审核后重复生成下游 | 幂等缺失、反审核再审核、接口重试 | 增加处理记录和重复判断 |
| 下推后字段为空 | 转换映射缺失、源分录关系丢失 | 查转换规则和源单关联 |
| 只有某个用户失败 | 权限、数据范围、字段权限 | 用管理员和普通用户对比 |
| 只有某组织失败 | 组织隔离、基础资料分配、参数差异 | 查组织参数和基础资料控制 |
| 批量审核很慢 | 循环查库、逐条调用外部接口 | 批量查询、异步推送、分批处理 |
| 发布后还是旧逻辑 | 环境没更新、缓存、包版本错 | 查发布记录和运行类版本 |
| 前台提示看不懂 | 直接抛技术异常 | 拆分用户提示和技术日志 |
| 生产能复现但测试不行 | 数据差异、参数差异、补丁差异 | 导出配置和关键数据比对 |

## 八、上线回归矩阵

插件上线不能只测“正常保存成功”。至少覆盖以下矩阵。

| 维度 | 回归项 |
| --- | --- |
| 单据状态 | 新增、保存、提交、审核、反审核、删除、关闭 |
| 分录 | 单行、多行、空行、合并行、拆分行 |
| 组织 | 单组织、跨组织、无权限组织 |
| 数据 | 必填为空、基础资料失效、编码重复、历史数据 |
| 金额数量 | 零数量、负数、超额、精度、币别、汇率 |
| 下游 | 下推、反写、反审核下游、删除下游 |
| 财务 | 凭证模板、应收应付、核销、存货核算、月结 |
| 接口 | 成功、失败、超时、重复请求、补偿重试 |
| 权限 | 菜单、按钮、字段、数据、工作流审批 |
| 性能 | 单张、批量、峰值、接口慢、数据库慢 |

### 发布前清单

- [ ] 需求和设计已评审。
- [ ] 插件触发对象和时机已确认。
- [ ] 元数据字段存在性已确认。
- [ ] 单元测试和集成测试通过。
- [ ] 关键业务用户 UAT 通过。
- [ ] 幂等、日志、异常提示完成。
- [ ] 数据修复或历史兼容方案确认。
- [ ] 发布包、配置包和版本号归档。
- [ ] 回滚方案写清楚。
- [ ] 上线观察人和观察窗口确认。

### 发布后观察

- [ ] 关键单据能保存、提交、审核。
- [ ] 插件日志有成功记录。
- [ ] 没有失败积压。
- [ ] 接口队列或外部系统无重复单。
- [ ] 凭证、库存、报表没有异常差异。
- [ ] 用户反馈的问题能定位到具体单据和日志。

## 九、案例：BOM 字段带入生产用料清单

这个案例用于说明“跨单据取上游分录字段，再写回当前分录”的治理方法。它不是通用代码模板，具体字段和单据标识必须按客户环境重新确认。

### 场景

生产用料清单分录需要带出 BOM 分录上维护的工艺、备注、标签等字段。用户希望在生产用料清单保存时自动写到当前分录，避免人工重复维护。

### 正确的追溯链路

```text
生产用料清单分录 stockentry
  -> bomentryid
  -> BOM 分录 pdm_mftbom.entry.id
  -> 读取 BOM 分录扩展字段
  -> 写回当前生产用料清单分录
```

关键点不是按物料编码查 BOM，而是用当前行保存的 `bomentryid` 找到真正的 BOM 分录。这样可以避免同物料、多 BOM、多版本、多分录时带错字段。

### 设计要点

| 要点 | 说明 |
| --- | --- |
| 插件类型 | 保存操作服务插件更合适，因为目标是保存时写回当前单据数据 |
| 查询条件 | 用 `bomentryid -> BOM entry.id` 追溯，不用物料名称 |
| 批量处理 | 先收集所有 `bomentryid`，再批量查 BOM 分录 |
| 字段映射 | 只写目标单据确实存在的字段 |
| 覆盖策略 | 明确是每次覆盖、为空才写，还是用户修改后不再覆盖 |
| 日志 | 记录单据编号、分录、BOM 分录、写入字段 |
| 回归 | 测多行、替代料、BOM 版本、反审核、重新保存、下游领料 |

### 不能直接照搬的地方

- 生产用料清单和委外用料清单可能字段不同。
- 一个插件可能除了目标字段，还写其他生产专用字段。
- 目标单据没有同名字段时不能强行写入。
- 如果目标单据的业务时机不同，需要重新选择触发时机。

### 排查清单

| 问题 | 排查 |
| --- | --- |
| 字段没带出 | 当前分录是否有 `bomentryid`，BOM 分录是否维护字段 |
| 只带出部分行 | 是否存在手工新增行、替代料行、无 BOM 来源行 |
| 带错值 | 是否按物料查而不是按 BOM 分录查 |
| 保存变慢 | 是否每一行都单独查 BOM |
| 委外单据不可用 | 委外目标字段是否真实存在，插件是否绑定正确单据 |

## 十、案例：审核后推送 WMS 重复

### 现象

销售出库单审核后推送 WMS。用户反审核修改后再次审核，WMS 收到两张相同外部单，仓库重复创建任务。

### 根因

- 审核后插件没有幂等记录。
- 外部系统没有以金蝶单据内码或外部业务号做唯一判断。
- 插件把“再次审核”当成“全新业务”处理。

### 改造方案

1. 建立接口处理记录，记录金蝶单据内码、单据编号、业务组织、目标系统、请求批次。
2. 第一次审核后推送成功，写成功状态。
3. 再次审核时先查处理记录。
4. 内容未变化则返回已推送，不重复创建。
5. 内容变化则发送变更消息或进入人工处理。
6. 反审核前检查 WMS 是否已经执行，如果已执行，需要按业务规则阻断或走撤销流程。

### 回归测试

- 首次审核推送。
- 反审核再审核不重复。
- 修改数量后再审核。
- 外部接口超时但实际已成功。
- 外部接口失败后补偿重试。
- WMS 已执行时金蝶反审核。
